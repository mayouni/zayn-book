## 1. What the chapter does

It gives the four levels of checking and what each one needs: the file alone twice, then a symbol table, then a rendered
surface. It shows a level 3 finding appear when the symbol table is supplied and stay silent without it. It shows the
conformance suite: fixtures with known verdicts, the manifest, the rule by which a run passes a fixture, why a fixture above a
verifier's level is skipped, which diagnostics have no fixture and why. It then shows several implementations held to one
verdict: the JavaScript reference, the `zayn` command held to it byte for byte, the same core compiled to WebAssembly, and a
court forged from the language declared in Haro, whose differences are named row by row. It tells the decision behind it:
fixtures and specification first, before any verifier could pass them.

## 4. The principle

The sentence the record returns to: **"Declarations with known verdicts, so any implementation in any language can prove
agreement rather than assert it."** (`conformance/README.md:3-4`). It returns in the pack ("agreement is proved by

Proposal for the chapter's bold sentence, in the book's words:

> **A verdict belongs to the suite: a fixture is a declaration kept with the answer it must get, and every verifier, in
> whatever language it is written, is held to that answer at the level it can see.**

A shorter form if the author prefers the decision in the sentence: **One verdict is kept by declarations with known answers,
written before any verifier could pass them.**

a verifier claims a level and the fixtures above it are skipped; a port is held to more than the suite (every byte of the
report); an evaluator made another way lists its differences one by one. The stake (C10) is the author's: an `[AUTHOR: …]`
hole.

## 11. Terms a designer who does not program needs

- **Level**: how much a verifier is given to see; the contract files each kind of finding at the level where it can be
  decided (`conformance/violations.json:10-14`).
- **Symbol table**: a small file that lists what the system around a declaration holds: its entities, its actors, its state
  and its elements (`tools/zayn/README.md:68`; `conformance/violations.json:13`). The reader writes it or a tool of the
  project does; the verifier reads it.
- **Entity, actor, state, element**: the four lists. An entity is a thing the system knows (a table, an order); an actor is
  who may act (an accountant); state is what the system currently holds (a filter that is on); an element is a thing on the
  surface (a card, a button). From the fixtures' own tables, `conformance/manifest.json:195-240`.
- **Rendered surface / painted page**: the interface once a browser has drawn it; level 4 needs it
  (`conformance/violations.json:14`). The book's word is the painted page.
- **Fixture**: a declaration kept with the answer it must get (`doc/decisions/M3-the-zane-verifier.md:163-164`; chapter 8).
- **Manifest**: the suite's list: each fixture's file, its level, the codes it must get, and its table if it needs one
  (`conformance/manifest.json`).
- **Conformance suite**: the fixtures and the manifest together; "the definition of agreement"
  (`doc/decisions/M3-the-zane-verifier.md:164`).
- **Verdict**: for a fixture, the set of codes a verifier reports; the suite compares that set and nothing else
  (`conformance/manifest.json:9`).
- **Pass, fail, skipped**: a run passes a fixture when its set of codes equals the expected set; it fails it otherwise; it
  skips a fixture filed above the level the verifier claims (`conformance/manifest.json:9-10`).
- **Lawful twin**: a second fixture where the defect is repaired and nothing else changes (`conformance/README.md:121-123`).
- **Reference**: the verifier the others are held to; here the JavaScript one (`tools/zayn/README.md:15-17`).
- **Port**: the same verifier written again in another language; the record's word for the `zayn` command
  (`doc/design/BINARY.md:123`).
- **Parity, byte for byte**: the two print the same characters, every one, and hand back the same exit code
  (`tools/zayn/parity.js:10-12`).
- **Corpus, seed**: inputs made by a program from the fixtures, to test beyond them; the seed is the number from which the
  same inputs are made again (`tools/zayn/parity.js:15-19`).
- **WebAssembly (wasm)**: a form of a program that a browser runs; here the verifier's core, so a page checks a declaration
  with nothing installed (`doc/design/BINARY.md:66-67`, `:139-140`).
- **Envelope**: the machine form of a finding, chapter 8's word; the proof compares envelopes (`tools/zayn/wasm-proof.html:69-71`).
- **Evaluator; the forged court**: any program that judges a declaration against the law; the forged court is the one made
  from the language's declaration in Haro (`site/haro.html:58-59`; `doc/design/BINARY.md:122`).
- **Ratchet**: a list of known differences that a check keeps from growing: a new difference fails, and so does a listed one
  that has gone (`haro/judge-zayn-court.js:6-9`).
- **Pack, hash**: the twelve files a participant pins; a hash is a short print of a file's bytes, which changes when one byte
  changes (`protocol/README.md:3`, `:48-49`).
